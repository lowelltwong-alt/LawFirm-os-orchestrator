# Design Rationale: Compute Intelligence For LawFirm OS

## Why token efficiency is not just dollar efficiency

Tokens cost money, but tokens also consume:

- latency;
- context-window space;
- reviewer attention;
- operational capacity;
- risk budget;
- opportunity budget;
- future readiness budget.

A cheap run can be bad if it creates rework, downstream ambiguity, or reputation exposure.

An expensive run can be good if it creates a reusable validator, a reusable eval harness, a high-value research option, or strategic readiness for a likely future capability shift.

## 4D compute efficiency

Compute should be evaluated across four dimensions:

1. Present value: Does the run solve a current bottleneck?
2. Future option value: Does the run prepare the OS for likely future states?
3. Strategic/game value: Does the run change the firm's position relative to competitors or counterparties?
4. Learning value: Does the run improve future decisions through Exception Lake evidence?

## Example: frontier math breakthrough readiness

If Research Radar assigns a credible probability that a frontier math or algorithmic breakthrough will arrive within three months, and a preparatory buildout would allow same-day advantage once verified, high-token prep may be justified.

But only if:

- the prep has fallback reuse value;
- the work does not grant unauthorized authority;
- the cost is staged rather than fully committed up front;
- Monte Carlo scenarios show positive risk-adjusted option value;
- the game-state analysis says first-mover advantage matters;
- the downside/reputation risk is bounded.

## Correct allocation doctrine

Do not minimize tokens.
Maximize risk-adjusted strategic value per unit of compute, latency, attention, and trust.
